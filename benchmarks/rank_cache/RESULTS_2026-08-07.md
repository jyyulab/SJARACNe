# Rank-cache benchmark results: 2026-08-07

## Result

Caching each gene's bootstrap-specific ranks substantially reduced AP-MI
runtime once the rank-building cost was shared across multiple hub-target
pairs. The representative 100-hub, 5,000-gene, 1,000-observation case fell from
53.93 seconds to 10.43 seconds: a 5.17x speedup. The 19,936-gene stress case
fell from 93.97 seconds to 22.19 seconds: a 4.23x speedup.

All 28 optimized adjacency outputs were byte-identical to the corresponding
baseline outputs. Because the deliberately unreachable timing threshold makes
these files header-only, MI correctness was checked separately with retained
edges: the full 48-test suite passed, including fixed legacy MI references for
tie-heavy bootstrap data and conditioning followed by bootstrap resampling.
Additional baseline/optimized comparisons covered no bootstrap, conditioning,
noise correction, and all-gene mode. All timing commands exited with status
zero and produced empty standard-error files.

The cost is memory. Median peak RSS rose by 12% to 18% across these cases. This
is expected because the optimized implementation stores one 32-bit rank for
each cached gene-observation combination.

## Hub-count sweep

Genes and observations were fixed at G=5,000 and N=1,000.

| Hubs | Baseline median wall time (s) | Optimized median wall time (s) | Speedup | Baseline / optimized median peak RSS (MiB) |
|---:|---:|---:|---:|---:|
| 1 | 1.34 | 1.06 | 1.26x | 107.6 / 126.6 |
| 10 | 6.19 | 1.90 | 3.26x | 107.7 / 127.0 |
| 50 | 27.37 | 5.70 | 4.80x | 108.0 / 127.1 |
| 100 | 53.93 | 10.43 | 5.17x | 107.9 / 127.1 |

The small gain at H=1 is expected: rank construction is paid once but is reused
for only one hub row. As H increases, the one-time rank cost is amortized over
more candidate edges.

## Observation-count sweep

Genes and hubs were fixed at G=5,000 and H=100.

| Observations | Baseline median wall time (s) | Optimized median wall time (s) | Speedup | Baseline / optimized median peak RSS (MiB) |
|---:|---:|---:|---:|---:|
| 100 | 3.89 | 1.47 | 2.65x | 15.5 / 17.4 |
| 250 | 10.05 | 3.09 | 3.25x | 30.9 / 35.7 |
| 500 | 23.02 | 5.54 | 4.16x | 56.6 / 66.1 |
| 1,000 | 53.93 | 10.43 | 5.17x | 107.9 / 127.1 |

The gain grows with N because the legacy implementation re-sorted two
N-element observation vectors for every candidate pair. The optimized
implementation sorts each cached gene once, then supplies its rank row directly
to adaptive partitioning.

## Gene-count sweep

Observations and hubs were fixed at N=500 and H=100.

| Genes | Repetitions | Baseline median wall time (s) | Optimized median wall time (s) | Speedup | Baseline / optimized median peak RSS (MiB) |
|---:|---:|---:|---:|---:|---:|
| 1,000 | 3 | 4.64 | 1.10 | 4.22x | 11.9 / 13.8 |
| 5,000 | 3 | 23.02 | 5.54 | 4.16x | 56.6 / 66.1 |
| 10,000 | 3 | 46.30 | 11.10 | 4.17x | 108.3 / 127.3 |
| 19,936 | 1 | 93.97 | 22.19 | 4.23x | 211.3 / 249.5 |

The near-constant speedup over G confirms that both versions still scale close
to linearly with the number of candidate targets in this fixed-H, fixed-N
range. The 19,936-gene row is a single stress run and should not be treated as
a stable median.

## Protocol

- Baseline commit: `fbad9e6` (`perf: add reproducible rank-cache benchmarks`)
- Optimized commit: `479c519` (`perf: cache gene ranks per bootstrap`)
- Arguments: `-S 17 -r 1 -t 100 -e 1`
- Execution: one SJARACNe process at a time; no competing benchmark process
- Repetitions: three per case except one run for the 19,936-gene stress case
- Statistic: median wall time and median maximum resident set size from GNU
  `time`; ranges and exact summary values are in `results_2026-08-07.csv`, and
  every timing observation is in `raw_timings_2026-08-07.csv`
- Timed binaries, inputs, and outputs: WSL native ext4 under `/tmp`, not a
  Windows-mounted path
- CPU: Intel Core i7-10700F at 2.90 GHz, 8 physical / 16 logical cores visible
  to WSL2
- OS: Ubuntu 24.04.3 LTS under WSL2, kernel
  `6.6.87.2-microsoft-standard-WSL2`
- Compiler: g++ 13.3.0 with the repository's release build flags
- Timing tool: GNU time 1.9

The threshold of 100 is deliberately unreachable and DPI is disabled. AP-MI is
still calculated for every candidate pair, while retained-edge serialization
and DPI cannot dominate the measurement. Across the exact 28-command schedule,
the sum of wall times fell from 627.34 seconds to 146.50 seconds (4.28x), but
that aggregate is schedule-weighted and is not a universal workload estimate.

## Correctness and safety validation

The complete Python/native/CWL test suite passed at the optimized commit:

```bash
python -m unittest discover -v -s tests -p 'test_*.py'
```

This ran 48 tests, including the end-to-end five-bootstrap acceptance workflow
and the two retained-edge rank-cache legacy references. A separate binary built
with AddressSanitizer and UndefinedBehaviorSanitizer also passed both rank-cache
reference tests and a 1,000-gene, 500-observation, 100-hub benchmark case. No
ASan, LeakSanitizer, or UBSan diagnostic was reported.

## Scope and limitations

This benchmark isolates bootstrap-specific rank preparation and AP-MI. It does
not measure the complete 100-bootstrap CWL workflow, process scheduling,
consensus construction, a retained-edge-heavy output, or DPI. It is therefore
evidence for the MI-kernel speedup, not a claim that every end-to-end SJARACNe
run will become 4x to 5x faster.

Only one machine, compiler, bootstrap seed, and source expression matrix were
used. Baseline cases ran before optimized cases rather than in randomized or
interleaved order, so cache, thermal, and run-order effects are not fully
controlled. The three-repeat cases were stable, with one slower baseline H=50
run (29.81 seconds versus 27.36 to 27.37 seconds for the other two). The
19,936-gene case was run once, and the generated H=500 and H=1,681 stress cases
were not timed. Future benchmarks should repeat the full workflow on the
intended workstation or HPC environment before selecting a production
parallelism policy.
